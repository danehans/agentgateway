## Summary

agentgateway currently load balances AI traffic across providers with Power of Two Choices (P2C), using health, latency,
and pending requests. This proposal adds an extensible AI load-balancing mechanism that can apply additional scheduling
signals before selecting a provider+model candidate.

The MVP keeps today's P2C behavior as the default when no AI load-balancing trigger matches the request. The first
opt-in strategy is `CostOptimized`, which uses existing model catalog data to bias provider selection toward lower
estimated cost while still respecting health, priority groups, and P2C final selection behavior.

The initial implementation is intentionally narrow:

- `AgentgatewayParameters` defines gateway-scoped AI load-balancing profiles and triggers, not a new CRD.
- Profiles are activated by request routing state, initially an effective model match such as `model: auto`.
- `AgentgatewayBackend.spec.ai.groups` remains the explicit provider+model candidate set.
- If no profile trigger matches, AI backends continue to use the current P2C provider selection.
- The first opt-in strategy is `CostOptimized`.
- Cost data comes from the existing model catalog ConfigMap flow, including catalogs generated by `agctl costs import`.
- Cost-optimized routing only schedules within explicit candidate sets; it does not add new silent model substitution.

## Background

Other AI gateways expose semantic or automatic model routing. LiteLLM supports auto routing based on semantic and
complexity signals. Kong supports semantic load balancing by embedding the request and matching it against model
descriptions. The Gateway API Inference Extension endpoint picker (now llm-d router) was based on the
[Kubernetes Scheduler](https://kubernetes.io/docs/concepts/scheduling-eviction/kube-scheduler/) and provides a useful
scheduler model: filter candidates, score eligible candidates, and select a target. This proposal adopts that shape for
AI provider+model selection while keeping the initial user-facing API small.

agentgateway already has the pieces to add a native, smaller version for AI model routing:

- `AgentgatewayBackend.spec.ai.groups` defines provider priority groups.
- AI provider selection uses P2C within the selected priority group.
- Virtual model routing can map a requested model alias to explicit target models.
- Model cost tracking already supports a provider+model catalog and models.dev import path.

The missing piece is a native scheduler that can use request and provider+model metadata before choosing an AI provider.

## Goals

- Add optional cost-optimized AI load balancing for explicit provider+model candidate sets.
- Preserve existing AI P2C behavior when no profile trigger matches.
- Introduce an extensible strategy framework for future filters, scorers, and request signals.
- Keep the MVP API simple by exposing named strategies instead of low-level scheduler plugins.
- Activate the MVP strategy through an effective model alias, such as `auto`, rather than a per-backend selector.
- Use the existing model catalog as the MVP cost data source.
- Support USD pricing only for the MVP while reserving an explicit `currency` field for future expansion.
- Fail closed when cost-optimized routing has no priced eligible candidates.
- Surface selected provider+model and routing decision metadata in logs, metrics, and traces.
- Surface invalid profile or pricing configuration through status conditions on the appropriate CRD.

## Non-Goals

- Add a new CRD for model routing, plugins, or scheduler profiles.
- Fetch models.dev data directly from the gateway at runtime.
- Add broad semantic model substitution in the MVP.
- Have the AI load-balancing strategy route arbitrary requested models to "similar enough" cheaper models.
- Support non-USD price conversion.
- Support every provider-native request shape in the MVP.
- Expose a user-configurable picker algorithm while P2C is the only supported final selection behavior.
- Replace service/workload endpoint load balancing.

## API

Add gateway-scoped AI load-balancing profiles to `AgentgatewayParameters`. These profiles are shared runtime
configuration for the Gateway's effective parameters.

```go
type AgentgatewayParametersSpec struct {
    ...
    // AI load-balancing profiles available to requests handled by this Gateway.
    //
    // +optional
    AILoadBalancing *AILoadBalancingParameters `json:"aiLoadBalancing,omitempty"`
}

type AILoadBalancingParameters struct {
    // +optional
    Profiles []AILoadBalancingProfile `json:"profiles,omitempty"`
}

type AILoadBalancingProfile struct {
    // +required
    // +kubebuilder:validation:MinLength=1
    Name string `json:"name"`

    // Request condition that activates this profile.
    //
    // +required
    Trigger AILoadBalancingTrigger `json:"trigger"`

    // Candidate filtering/scoring strategy for this profile. The MVP uses P2C
    // as the final selection algorithm for all strategies.
    //
    // +optional
    // +kubebuilder:validation:Enum=P2C;CostOptimized
    // +kubebuilder:default=P2C
    Strategy AILoadBalancingStrategy `json:"strategy,omitempty"`

    // Cost config. Required when strategy is CostOptimized.
    //
    // +optional
    Cost *CostOptimizedLoadBalancing `json:"cost,omitempty"`
}

type AILoadBalancingTrigger struct {
    // Effective model name that activates this profile, for example "auto".
    // The effective model is the model after existing request transformations,
    // content routing, and model aliasing have produced trusted routing state.
    //
    // +required
    Model ShortString `json:"model"`
}

type CostOptimizedLoadBalancing struct {
    // Default output token estimate when the request does not provide max tokens.
    //
    // +optional
    // +kubebuilder:default=512
    DefaultOutputTokens *int32 `json:"defaultOutputTokens,omitempty"`

    // Behavior when a candidate has no usable price.
    //
    // +optional
    // +kubebuilder:validation:Enum=FailClosed
    // +kubebuilder:default=FailClosed
    MissingPrice MissingPriceBehavior `json:"missingPrice,omitempty"`
}
```

Custom providers need a stable cost lookup identity. Managed providers derive this from the provider type, such as
`openai` or `anthropic`. Custom providers should use an explicit model-catalog identity instead of overloading provider
identity. This lets an operator price a locally hosted OSS model differently from the same model served by a commercial
provider.

The existing model catalog can already hold arbitrary provider keys. The MVP should let a custom provider point at one
of those keys:

```go
type CustomProvider struct {
    ...
    // Cost lookup configuration for this custom provider.
    //
    // +optional
    Cost *CustomProviderCost `json:"cost,omitempty"`
}

type CustomProviderCost struct {
    // Model catalog entry used for cost lookup.
    //
    // +optional
    Catalog *CustomProviderCostCatalogRef `json:"catalog,omitempty"`
}

type CustomProviderCostCatalogRef struct {
    // Provider key in the model catalog. If unset, custom providers use "custom".
    //
    // +optional
    Provider *ShortString `json:"provider,omitempty"`

    // Model key in the model catalog. If unset, agentgateway uses custom.model
    // when set, otherwise the requested model.
    //
    // +optional
    Model *ShortString `json:"model,omitempty"`
}
```

Example:

```yaml
apiVersion: agentgateway.dev/v1alpha1
kind: AgentgatewayParameters
metadata:
  name: agw
spec:
  modelCatalog:
    sources:
    - configMap:
        name: model-costs
        key: catalog.json
  aiLoadBalancing: # optional and uses existing P2C when unspecified
    profiles:
    - name: auto-cost
      trigger:
        model: auto
      strategy: CostOptimized
      cost:
        defaultOutputTokens: 512 # optional
        missingPrice: FailClosed # optional
```

```yaml
apiVersion: agentgateway.dev/v1alpha1
kind: AgentgatewayBackend
metadata:
  name: llm
spec:
  ai:
    groups:
    - providers:
      - name: openai-mini
        openai:
          model: gpt-4o-mini
      - name: anthropic-haiku
        anthropic:
          model: claude-3-5-haiku-latest
```

Validation:

- `aiLoadBalancing` is optional. If unset, AI backends use the current P2C provider selection behavior.
- Each profile must define a trigger. The MVP supports `trigger.model`.
- `trigger.model` values must be unique within the Gateway's effective `AgentgatewayParameters`.
- `CostOptimized` requires a configured model catalog source.
- `CostOptimized` supports only `missingPrice: FailClosed` in the MVP.
- `custom.cost.catalog.provider`, when set, must be a valid non-empty model catalog provider key.
- Unsupported request formats are rejected at runtime with a clear error. Static validation should catch unsupported
  formats only when the controller has enough information to do so.

Profile trigger resolution is gateway-scoped. If the same `AgentgatewayBackend` is referenced by routes attached to
different Gateways, each Gateway evaluates triggers from its own effective `AgentgatewayParameters`.

## Existing Model Routing and Candidate Sets

Cost-optimized routing only operates over explicit candidates. A profile is activated when its trigger matches the
effective model for the request, such as `auto`. This does not prevent existing agentgateway routing features from
deriving or rewriting the effective model before AI load balancing runs.

The MVP candidate set is the providers configured for the selected `AgentgatewayBackend` priority group, including the
provider model configured on each provider. Existing virtual model or alias configuration may also contribute explicit
candidate models, as long as the scheduler is still choosing only from configured candidates.

Existing features such as content-based routing and multiple `InferencePool` routing can continue to inspect the request
body, derive routing metadata, select a route/backend, or map a user-facing model to an effective backend/model. The AI
load-balancing trigger is evaluated after that routing context is known. If a trigger matches, the selected profile
schedules within the explicit candidates for the selected AI backend. If no trigger matches, agentgateway uses the
current P2C provider selection behavior.

The new AI load-balancing strategy must not independently rewrite an arbitrary requested model to a different model
unless that target model is part of the selected backend's explicit candidate set. Broader semantic substitution can be
added later as an opt-in strategy.

## Custom Providers

Custom providers participate in AI load balancing the same way managed providers do. The AI load-balancing decision is
made before resolving the selected provider's concrete target.

This applies to all custom provider target forms:

- `host + port`
- `backendRef` to `Service`
- `backendRef` to `InferencePool`

For `host + port` and `Service` targets, the selected custom provider is called directly after AI load balancing and the
normal LLM request pipeline completes.

For a custom provider that targets an `InferencePool`, request handling has an additional endpoint-selection stage:

```text
AI load balancing:
  choose provider+model candidate from AgentgatewayBackend.spec.ai.groups

InferencePool routing:
  if the selected custom provider targets an InferencePool,
  run the existing inferenceRouting/EPP flow to choose a pool endpoint
```

The AI load-balancing strategy chooses a model/provider candidate; it does not choose an `InferencePool` endpoint. The
EPP flow chooses the endpoint inside the selected pool; it does not choose the model. `host + port` and `Service` custom
targets do not run EPP unless they otherwise have inference routing configured through the existing backend path.

Cost-optimized routing requires each custom candidate, regardless of target type, to have a price:

- Cost provider identity is `custom.cost.catalog.provider` when set, otherwise `custom`.
- Cost model identity is `custom.cost.catalog.model` when set, otherwise `custom.model` when set, otherwise the
  requested model.
- The selected provider's `formats` still determine which request shapes the custom provider can serve.
- If a custom candidate has no matching provider+model catalog entry, that candidate is ineligible.
- Priority groups are evaluated in order. Cost-optimized routing selects from the first priority group that has at
  least one eligible, priced candidate. If no priority group has an eligible priced candidate, the request fails closed.

Example catalog keys:

```json
{
  "providers": {
    "local-vllm": {
      "models": {
        "llama-3.1-8b": {
          "rates": {
            "input": "0.05",
            "output": "0.10"
          }
        }
      }
    }
  }
}
```

```yaml
providers:
- name: local-vllm
  custom:
    model: llama-3.1-8b
    cost:
      catalog:
        provider: local-vllm
    backendRef:
      group: inference.networking.k8s.io
      kind: InferencePool
      name: llama-pool
    formats:
    - type: Completions
```

## Future Weighted Strategies

The MVP exposes named strategies rather than low-level scheduler configuration. Future strategies can add a `Composite`
mode for operators who need to combine multiple scheduling signals.

In that model, filters remain hard gates and scorers produce normalized scores where higher is better. Weights express
relative importance. Processing order should not affect scoring semantics, but implementations may still order expensive
signal collection for efficiency.

Example:

```yaml
aiLoadBalancing:
  profiles:
  - name: cache-first
    trigger:
      model: auto
    strategy: Composite
    composite:
      filters:
      - type: Priced
      - type: SupportsRoute
      scorers:
      - type: ApproximatePrefixCache
        weight: 0.8
      - type: Cost
        weight: 0.2
```

This profile would prefer likely prefix-cache hits over lower cost, while still using the same P2C final selection
algorithm. The weighted score only changes which sampled candidate is considered better.

## Runtime Design

Add a native AI scheduling layer in the LLM path after route/backend/model resolution and before concrete provider
selection.

Conceptually:

```text
select route
  -> resolve AgentgatewayBackend
  -> extract requested and effective model
  -> build explicit provider+model candidates
  -> if no ai load-balancing trigger matches:
       use existing AIBackend::select_provider()
     else:
       run the matched AI load-balancing profile strategy
  -> resolve selected provider target
  -> run existing LLM request pipeline
  -> call upstream
```

Initial internal types:

```rust
struct ModelCandidate {
    provider_name: Strng,
    provider_id: Strng,
    provider_model: Strng,
    public_model: Strng,
    endpoint_info: EndpointInfo,
}

struct ModelRequest {
    requested_model: Strng,
    effective_model: Strng,
    route_type: RouteType,
    estimated_input_tokens: u64,
    estimated_output_tokens: u64,
}

enum AILoadBalancingStrategy {
    P2C,
    CostOptimized(CostOptimizedConfig),
}
```

`AILoadBalancingStrategy` controls how candidates are filtered and compared, not the final selection algorithm. In the
MVP, P2C remains the only final selection algorithm. The `P2C` strategy is today's health/load comparison behavior,
while `CostOptimized` adds cost filtering and a cost-aware comparator before using the same P2C final selection.

Profile triggers are evaluated against trusted request state computed by agentgateway, not raw client-supplied routing
headers. A client can request `model: auto`, or an existing transformation/content-routing rule can derive `auto` as the
effective model. agentgateway should own or overwrite any internal metadata used for the trigger before scheduling.

The runtime should keep the strategy implementation extensible. `CostOptimized` can be implemented as the first
non-default scheduling strategy, internally composed from candidate filtering, cost scoring, and P2C selection. Future
strategies can add request classification, prefix-cache signals, capability filters, latency weighting, or custom
scorers without changing the default backend behavior.

For `CostOptimized`:

1. Parse enough of OpenAI-compatible chat/responses requests to identify the requested/effective model and estimate
   input tokens.
2. Estimate output tokens from request `max_tokens` / `max_output_tokens`, otherwise use `defaultOutputTokens`.
3. Build candidates that resolve to concrete provider models. A candidate that would forward `auto` upstream is
   ineligible.
4. Look up each candidate's provider+model rates in the model catalog.
5. Exclude unpriced candidates when `missingPrice: FailClosed`.
6. Evaluate priority groups in order and select from the first group with at least one eligible priced candidate.
7. If no priority group has an eligible priced candidate, reject the request.
8. Use P2C within the selected priority group. P2C samples two candidates, then compares them lexicographically:
   1. existing availability/health eligibility and health state;
   2. priced eligibility, which is a hard filter for the MVP;
   3. lower estimated request cost;
   4. existing P2C health/load/latency/pending-request comparison as the tie-breaker.
9. Rewrite the upstream request model to the selected provider model.

This comparator is intentionally not a multiplicative score such as `health_score * cost_score`. Cost must not let a
cheaper unhealthy or unavailable provider beat a healthier priced provider. When two sampled candidates have the same
estimated cost, the decision is identical to today's P2C comparison for those candidates.

## Cost Data

The MVP data source is the existing model catalog.

Operators can generate a catalog from models.dev with:

```text
agctl costs import
```

and load it through `AgentgatewayParameters.spec.modelCatalog`.

The runtime should add an estimate API alongside the existing response-time cost projection logic. The estimate path uses
the same provider+model catalog data but operates before the upstream request is sent.

Custom provider pricing should use the same catalog. Operators can manually add provider keys such as `local-vllm`,
`in-cluster-llama`, or `private-gpu-pool` and point custom providers at those entries with `custom.cost.catalog`. This
keeps locally hosted OSS model pricing distinct from the same model served by a commercial provider.

A future catalog enhancement could add first-class custom deployment aliases if arbitrary provider keys are not
ergonomic enough. The MVP should keep the existing provider/model catalog schema and add only the custom provider cost
identity needed to look up those entries.

## Controller and xDS

Controller changes:

- Add `aiLoadBalancing` to `AgentgatewayParameters`.
- Add `spec.ai.groups[].providers[].custom.cost.catalog` for custom provider model catalog lookup.
- Validate `aiLoadBalancing` profile triggers in the Gateway's effective `AgentgatewayParameters`.
- Validate `CostOptimized` profile requirements.
- Set status conditions when profile or pricing configuration is invalid or incomplete.
- Translate profile trigger and strategy configuration into the generated proxy config.

Dataplane/proto changes:

- Add AI load-balancing profile config to the proxy config.
- Add profile trigger matching to the dataplane AI routing configuration.
- Carry custom provider cost catalog identity to the dataplane separately from provider wire behavior.
- Preserve the existing wire format when no trigger matches.

## Status Conditions

The controller should surface configuration problems instead of silently falling back.

Examples:

- `Accepted=False`, `Reason=InvalidAILoadBalancingProfile` when profile triggers are invalid or duplicated.
- `Accepted=False`, `Reason=InvalidAILoadBalancingProfile` when `CostOptimized` is configured without a model catalog.
- `ResolvedRefs=False`, `Reason=InvalidModelCatalog` when the referenced catalog ConfigMap is missing or malformed.
- `Accepted=False`, `Reason=UnpricedAICandidates` when a cost-optimized trigger has no priced eligible candidates for a
  referenced AI backend.

If only some candidates are unpriced, the backend can still be accepted, but status should identify the skipped
provider+model pairs when practical. At runtime, those candidates are ineligible for cost-optimized selection.

Runtime request failures caused by fail-closed pricing should return a clear 5xx configuration-style error and include a
log field explaining that no priced candidates were available.

## Observability

Add first-class telemetry fields for AI load-balancing decisions:

- requested model
- effective model
- matched AI load-balancing trigger
- selected provider
- selected provider model
- selected AI load-balancing profile
- selected strategy
- estimated input tokens
- estimated output tokens
- estimated cost, when available
- reason for rejection, when no candidate is eligible

These fields should be available to access logs, metrics labels where cardinality is acceptable, and traces.

## Compatibility and Migration

Existing users are unaffected.

Requests whose effective model does not match an `aiLoadBalancing` trigger continue to use the current P2C behavior.
Operators opt in by:

1. Loading a model catalog through `AgentgatewayParameters.spec.modelCatalog`.
2. Defining a gateway-scoped `aiLoadBalancing` profile with `trigger.model: auto` and `strategy: CostOptimized`.
3. Sending requests with `model: auto`, or using existing content-routing/transformation behavior to derive `auto` as
   the effective model for selected traffic.
4. Ensuring the selected `AgentgatewayBackend` has explicit provider+model candidates for the scheduler to choose from.

## Risks and Tradeoffs

- **Cost estimates are approximate.** Output tokens are unknown before the request completes. The MVP uses request max
  token settings or a configurable default.
- **Fail closed can reduce availability.** This is intentional for cost-optimized routing, but operators must provide
  complete pricing for all intended candidates.
- **P2C is not exact cheapest.** P2C samples two eligible candidates and chooses the better one, preserving current
  balancing behavior while biasing toward lower cost.
- **MVP request parsing is limited.** Only OpenAI-compatible chat/responses-style requests are supported initially.
- **No arbitrary semantic substitution.** This avoids surprising callers who requested a specific model.
- **Trigger metadata must be trusted.** agentgateway should derive or overwrite internal trigger metadata before
  scheduling. Raw client-supplied headers are classification hints, not a security or spend-control boundary.

## Test Plan

- API validation accepts omitted `spec.aiLoadBalancing`.
- API validation rejects duplicate `trigger.model` values.
- API validation rejects invalid `CostOptimized` profile config.
- Controller translation preserves existing AI backend output when no trigger matches.
- Controller translation includes trigger and strategy config when configured.
- Runtime uses existing P2C when the effective model does not match a trigger.
- Runtime uses the matched profile when the effective model matches `auto`.
- Runtime rejects candidates that would forward `auto` upstream without resolving to a concrete provider model.
- Cost estimation uses provider+model catalog rates.
- Cost estimation uses `custom.cost.catalog.provider` and `custom.cost.catalog.model` for custom provider catalog lookup
  when set.
- Custom `InferencePool` candidates are selected by AI load balancing before EPP endpoint selection.
- Cost estimation uses request max output tokens when present.
- Cost estimation falls back to `defaultOutputTokens` when max output tokens are absent.
- Unpriced candidates are excluded.
- Requests fail when all candidates are unpriced.
- Health/unhealthy candidate behavior remains respected.
- Access logs/traces include effective model, matched trigger, selected provider+model, and strategy metadata.
- Existing AI P2C and virtual model routing tests continue to pass.
